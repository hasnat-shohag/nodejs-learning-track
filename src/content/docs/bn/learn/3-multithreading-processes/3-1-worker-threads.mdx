## এই লেসনে যা শিখবেন

`new Worker(file)` বানায় একটি দ্বিতীয় V8 আইসোলেট, নিজের event loop-সহ, নিজের OS থ্রেডে, একই প্রসেসের ভেতরে — এক `pid`, দুই `threadId`। ডিফল্টে দুই আইসোলেটের মাঝে কিছুই শেয়ার হয় না, আর এটাই ফিচার: JS heap-এ লক লাগে না, কারণ শেয়ার করা JS heap নেই। যোগাযোগ হয় `postMessage` দিয়ে, আর এর দুই মোডই এই লেসনের হৃদয়। transfer list ছাড়া পাঠালে মেসেজ **structured clone** হয় — রানটাইম ভ্যালু হাঁটিয়ে কপি করে, তাই 64 MB `ArrayBuffer` মানে 64 MB কপি খরচ, আর প্রেরকের কপি থেকেই যায়। buffer-টা transfer list-এ দিলে ব্যাকিং মেমরি **সরে যায় (transfer)** — রিসিভার বাইট পায়, আর `postMessage` ফেরার সাথে সাথে প্রেরকের ভিউ detach হয় (`byteLength === 0`)। শূন্য কপি, আর প্রেরক আর কোনোদিন ওই ডেটা ছুঁতে পারে না।

<Pitfall title="Transfer সাথে সাথে buffer detach করে — worker পড়ার আগেই">
	<p>
		`postMessage(msg, [buf])` কলের সময়েই প্রেরকের `buf` অচল হয়, worker পড়লে নয়। কলের পরের কোড `byteLength === 0` দেখে — পরে একই buffer আবার পাঠাতে গেলে `DataCloneError` ছোড়ে। আর **MessageChannel** হলো আপনার তৃতীয় পোর্ট-জোড়া: দুই worker সরাসরি কথা বলার রাস্তা, প্যারেন্টকে রিলে করতে হয় না। একটি চ্যানেল বানান, প্রতি পাশে এক পোর্ট ধরিয়ে দিন, আর মেসেজ main থ্রেডকে ঘুরিয়ে না দিয়ে ওদের মাঝেই চলে।
	</p>
</Pitfall>

## এক প্রসেস, দুই থ্রেড, দুই postMessage মোড

এই লেসনের ডেমো ফাইলটি চালান:

```bash
node code/3-multithreading-processes/3-1-worker-threads/demo.js
```

ছাপে: `[1]` main থ্রেডের `threadId` আর pid; `[2]` worker-এর — একই pid, ভিন্ন `threadId`, দুই-আইসোলেটের ছবি চোখের সামনে। `[3]` transfer list ছাড়া পাঠানো 64 MB buffer: worker বাইট পায়, main-এর কপি পুরোটাই আছে — clone, একটি ফুল কপি। `[4]` একই buffer transfer করলে: `postMessage`-এর পরেই main-এর `byteLength` `0`, worker পায় একই মেমরি — সরানো, কপি নয়।
