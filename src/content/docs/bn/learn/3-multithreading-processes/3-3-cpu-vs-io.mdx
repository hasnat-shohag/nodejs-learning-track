## এই লেসনে যা শিখবেন

"এটা Worker-এ যাবে?" — উত্তর দুই শব্দে: কাজটা *কীসের জন্য অপেক্ষা করে* সেটার ওপর নির্ভর করে। **CPU-bound** কাজ — hashing, parsing, compression, ইমেজ প্রসেসিং — থ্রেড ধরে রাখে, আর সেই থ্রেড main হলে event loop ধরে রাখে: প্রতিটি callback, প্রতিটি request, প্রতিটি পিং পেছনে লাইনে। Worker-এ সরালে main লুপ মুক্ত থাকে: কাজের CPU খরচ একইই, কিন্তু responsiveness অক্ষত। **I/O-bound** কাজ — ফাইল রিড, নেটওয়ার্ক কল, DB কোয়েরি — অপেক্ষা করে অপারেটিং সিস্টেমের জন্য, আপনার JS-এর জন্য নয়। Event loop ঠিক এর জন্যই বানানো: request OS-কে ছুড়ে দেয়, completion পরে সামলায়। ওটাকে Worker দিলে যোগ হয় এমন একটি থ্রেড যার সারাজীবন অপেক্ষা — খাঁটি ওভারহেড। এই লেসন তিনটি ক্ষেত্রই মাপে এক প্রোব দিয়ে: 25ms-এর পিং টাইমার, যার সবচেয়ে খারাপ gap-ই কাজের বসানোর দাম।

## এক প্রোব, তিন বসানো

এই লেসনের ডেমো ফাইলটি চালান:

```bash
node code/3-multithreading-processes/3-3-cpu-vs-io/demo.js
```

ছাপে: `[1]` main লুপে 300ms sync CPU — সবচেয়ে খারাপ পিং gap পুরো বার্ন পর্যন্ত লাফায়, লুপ ব্লকড ছিল; `[2]` একই 300ms CPU Worker-এর ভেতরে — পিং স্বাভাবিক ফাঁকে সমতল, লুপ টেরও পায়নি; `[3]` CPU-bound কাজ Node নিজেই সরিয়ে রাখে — libuv thread pool-এ pbkdf2 হ্যাশিং — পিং আবার সমতল: বার্ন pool-এর থ্রেডে চলে, এই থ্রেডে নয়, আর কল queue হতেই লুপ মুক্ত।
