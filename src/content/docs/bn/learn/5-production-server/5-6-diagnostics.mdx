## এই লেসনে যা শিখবেন

**perf_hooks**-এর `monitorEventLoopDelay()` একটা histogram দেয় যা loop turn-এর ফাঁক স্যাম্পল করে — প্রসেসের আসল latency, প্রতিটা request আর timer যেটা অনুভব করে। ~৯০ms blocking `pbkdf2Sync` কল loop মাঝ turn-এ জমিয়ে রাখে, আর histogram সেটা রেকর্ড করে একই সাইজের delay spike হয়ে — কিন্তু শুধু যন্ত্র সৎ পড়া পেলে: বড় ফাঁকটা block-এর *পরের* loop turn-এ রেকর্ড হয়, আর stall-এর চেয়ে মোটা resolution (৯০ms block-এ ১০০ms স্যাম্পল) ফাঁকটাকে কোনো স্যাম্পলেই ধারে না। দুটোই যন্ত্র অন্ধ করার পথ, প্রসেস তখনো ভুগছে — ডেমোর সতর্কবার্তা ঠিক সেটাই। Timer-এর পাশ থেকে ওই stall একই সত্য: ২০ms-এর `setInterval` ticker ~৮৫ms দেরি চলে, কারণ block চলাকালীন পাওনা tick তার পেছনে queue হয়। Latency SLA ভাঙা এখানেই আগে ধরা পড়ে, যেকোনো dashboard-এর আগে — queue হওয়া প্রতিটা request আর timer পুরো ফাঁকটাই অপেক্ষা করে। প্রসেসের ভেতরের যন্ত্র না যথেষ্ট হলে **--inspect** (বা `SIGUSR1`) চালু সার্ভারে DevTools debugging চ্যানেল খোলে, আর heap snapshot উত্তর দেয় "মেমরি খাচ্ছে কী" — rss বাড়লে। দুটোই রুটিন নয়, diagnosis-এর শেষ হাতিয়ার: যে metric আপনি *watch* করেন সেটা loop delay, rss drift, event-loop lag percentile — ঘুমের মধ্যে চলা stall detector।

## ভেতর থেকে loop দেখুন, বাইরে থেকে যুক্ত হোন

এই লেসনের ডেমো ফাইলটি চালান:

```bash
node code/5-production-server/5-6-diagnostics/demo.js
```

ছাপে: `[1]` `resolution: 1`-এ `monitorEventLoopDelay`-এ মাপা ~৯০ms blocking কল — loop যেমন টের পেয়েছে, সাথে যন্ত্র অন্ধ করার দুই পথ; `[2]` timer-এর পাশ থেকে একই stall — ২০ms ticker ~৮৫ms দেরি, drift সমান block; `[3]` প্রসেসের ভেতর থেকে prod checklist: leak-প্রার্থী rss/heapUsed, debugger-এর জন্য `--inspect`/`SIGUSR1`, rss বাড়লে heap snapshot।
