## What you will learn

"Node is single-threaded" is only about your JavaScript. Some async work — file system calls, DNS lookups (when not `c-ares`), `crypto.pbkdf2`, `zlib` — is too, because the OS has no non-blocking form of it. libuv runs that work on a **thread pool**: four OS threads by default, spun up on first use and sized from the environment then — in practice, set `UV_THREADPOOL_SIZE` before `node` starts; setting it in code is not guaranteed and does nothing once the pool exists. Six pool jobs therefore run as **two waves** of four and two. This lesson shows you the waves, and what `UV_THREADPOOL_SIZE` does to them.

<Pitfall title="The pool is a shared bottleneck">
	<p>
		Those four threads serve <strong>every</strong> pool task in the process — one slow `fs.stat` on a cold NFS mount delays every `pbkdf2` behind it, and vice versa. Setting `UV_THREADPOOL_SIZE` higher looks free, but each thread costs a stack (~1MB) and more contention; the pool also stops being the bottleneck only if CPU and disk actually parallelize. Diagnose with `perf_hooks`/`--trace-sync-io` before tuning.
	</p>
</Pitfall>

## Watch the waves

Run the demo file for this lesson, then with a doubled pool:

```bash
node code/1-node-anatomy-event-loop/1-5-libuv-thread-pool/demo.js
UV_THREADPOOL_SIZE=8 node code/1-node-anatomy-event-loop/1-5-libuv-thread-pool/demo.js
```

Six `pbkdf2` jobs at default size finish in two clusters — four together, then two — while your JS thread stays free the whole time. At size 8, all six land in one cluster. Note the pool reads `UV_THREADPOOL_SIZE` when it first spins up; setting `process.env.UV_THREADPOOL_SIZE` in code after the pool exists does nothing.
