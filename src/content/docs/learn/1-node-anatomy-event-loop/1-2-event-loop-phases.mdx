## What you will learn

The event loop is not a queue — it is a **cycle of phases**. Each turn, libuv visits: **timers** (due `setTimeout`/`setInterval` callbacks), **pending** (some I/O results), **idle/prepare** (internal), **poll** (wait for new I/O events and run their callbacks), **check** (`setImmediate` callbacks), then **close** (teardown callbacks like a socket's `'close'`). This lesson walks one turn, phase by phase, and shows you the one ordering rule interview questions actually test: inside an I/O callback, `setImmediate` beats `setTimeout(…, 0)`.

<Pitfall title="'setTimeout(fn, 0)' is not 'run next'">
	<p>
		A 0ms timeout does not run after your current code — it waits for the <strong>next timers phase</strong>, which is a full loop turn away. If you schedule work from inside an I/O callback and want it in the <em>same</em> turn, `setImmediate` runs in the <strong>check</strong> phase, right after the current poll phase ends. That is why the order flips: at top level the two are a coin flip; from inside poll, immediate always wins.
	</p>
</Pitfall>

## One turn, four visible phases

Run the demo file for this lesson:

```bash
node code/1-node-anatomy-event-loop/1-2-event-loop-phases/demo.js
```

It prints one loop turn in order: the **timers** phase fires a 0ms `setTimeout`, the **poll** phase delivers a real `fs.readFile` event, and the **check** phase runs `setImmediate` — including the flipped order when both are scheduled <em>from inside</em> the poll callback, where immediate no longer has to wait for a next turn's timers phase.
