## What you will learn

One line of hot-loop JavaScript can stall a server for every connected client at once — because the blocked thread is the **only** thread your callbacks run on. The cost model is simple: **lag is paid by every pending callback, once, in full**. This lesson makes that visible with a probe: a 50ms interval ping whose gaps grow by exactly the block time, next to the same 200ms of CPU work sliced with `setImmediate` — where no gap grows at all.

<Pitfall title="monitorEventLoopDelay won't show you a spike as it happens">
	<p>
		`monitorEventLoopDelay()` is the documented tool, but its histogram updates on an interval and its resolution floors around a millisecond — a single 200ms block can read as ordinary jitter in the moment. The self-ping probe in the demo (schedule `setInterval`, measure gaps) is dumber and honest: every gap is a direct lag sample. Prefer it when the question is "how bad was that one request".

## The probe: 50ms pings never lie

Run the demo file for this lesson:

```bash
node code/1-node-anatomy-event-loop/1-4-blocking-the-loop/demo.js
```

The probe fires every 50ms and records each gap. A 200ms synchronous spin lands inside one probe window: that gap prints as ~250 (50 + 200). Then the demo runs the same 200ms of work in 5ms slices with `setImmediate` re-arming — every gap stays ~50. Same work, same wall time; only one of them kept a server responsive.
