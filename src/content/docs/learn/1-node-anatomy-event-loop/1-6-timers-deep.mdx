## What you will learn

Timers are the event loop's most abused API. This lesson pins the three behaviors people get wrong: **ref/unref** — `unref()` only removes a timer's vote to keep the process alive, it does not cancel it; **re-arming** — a `setTimeout` scheduled from inside a timer callback runs on a *later loop turn*, it is not recursion; and **interval drift** — when a callback runs long, missed dues are *dropped*, so a 100ms interval under a 150ms callback fires late once, then continues on its grid. No catch-up bursts, ever.

<Pitfall title="'I unref-ed it, why did it still fire?'">
	<p>
		Because something else kept the loop alive. `unref()` says "this timer alone may not keep the process up" — if an open server or another ref-ed timer holds the loop open, your unref-ed timer still fires on schedule. The demo proves it: an unref-ed 50ms timeout fires anyway while a ref-ed interval runs, and a child process with <em>only</em> an unref-ed timer exits immediately.
	</p>
</Pitfall>

## Three behaviors, one demo

Run the demo file for this lesson:

```bash
node code/1-node-anatomy-event-loop/1-6-timers-deep/demo.js
```

Four sections print: unref-ed timer firing anyway (`fired=true`); a child exiting with a timer pending; `ref()` restoring keep-alive; and a drift probe — a 100ms interval whose first callback blocks 150ms prints gaps `100 150 100 100 100`: one late fire, two dropped dues, then back on grid. Re-read the gaps against the rule: **fires never run early, and never repay misses**.
