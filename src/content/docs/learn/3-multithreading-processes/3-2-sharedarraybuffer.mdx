## What you will learn

`postMessage` copies; sometimes you want two threads on the *same* bytes — an image being processed, a shared counter, a ring buffer. **SharedArrayBuffer** (SAB) is that: raw memory both isolates can map, zero copy on either side. But shared bytes break the single-threaded assumption JS is built on. `view[0] += 1` is three operations — load, add, store — and two threads running it on the same cell can both load the same old value, both add, both store, and one increment vanishes. That is a **data race**, not a rare theory: on a 30 M + 5 M increment load this lesson's demo loses millions of updates. The fix is **Atomics**: `Atomics.add(view, 0, 1)` is one indivisible operation — every increment lands. `Atomics.wait` / `Atomics.notify` complete the toolkit: put a thread to sleep at the OS level, no CPU spin, and wake it from the other side.

<Pitfall title="A small symmetric load can look race-free — you tested serial, not concurrent">
	<p>
		Run 10k + 10k increments and you will often see exactly 20k — and learn nothing. Both loops may run back-to-back serially, or the window is so short the race never fires. The demo's main side loops 30 M times (~60 ms) so the worker's 5 M provably overlap it; only then does the lost-update gap open. When you benchmark races, size the load for guaranteed overlap — asymmetric, with the main side still hot when the worker joins.
	</p>
</Pitfall>

## Lose a race, then win it

Run the demo file for this lesson:

```bash
node code/3-multithreading-processes/3-2-sharedarraybuffer/demo.js
```

It prints: `[1]` the race — plain `view[0] += 1` from both sides lands well under the expected 35 M; `[2]` the same load with `Atomics.add` on both sides — exactly 35 M, every increment accounted for; `[3]` `Atomics.wait` parking the main thread at the OS level until the worker's `Atomics.notify` wakes it — sleep without spinning, measured in the wake-up gap.
