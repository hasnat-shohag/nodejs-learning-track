## What you will learn

"Should this go in a Worker?" has a two-word answer: it depends on what the work *waits on*. **CPU-bound** work — hashing, parsing, compression, image processing — holds the thread, and if that thread is the main one it holds the event loop, and every callback, every request, every ping queues up behind it. Move it to a Worker and the main loop stays free: the work still costs the same CPU, but responsiveness is untouched. **I/O-bound** work — file reads, network calls, DB queries — waits on the operating system, not on your JS. The event loop was built for exactly this: it kicks the request to the OS and handles the completion later. Giving it a Worker adds a thread that spends its life *waiting*, which is pure overhead. This lesson measures all three cases with one probe: a 25 ms ping timer whose worst gap is the price of the work's placement.

<Pitfall title="A quiet probe proves nothing — timing pings during a block">
	<p>
		Measuring event-loop health with a ping timer has a trap: during a synchronous block the probe *cannot fire*, so a naive reading shows nothing wrong. The demo resets the gap list, sleeps 50 ms to let one normal ping land, runs the block, then sleeps again — the first ping *after* the block carries the whole damage in its gap. The pattern to steal: always bracket the thing you are measuring with sleep on both sides, and read the worst gap, not the average.
	</p>
</Pitfall>

## One probe, three placements

Run the demo file for this lesson:

```bash
node code/3-multithreading-processes/3-3-cpu-vs-io/demo.js
```

It prints: `[1]` 300 ms of sync CPU on the main loop — the worst ping gap spikes to the full burn, the loop was blocked; `[2]` the same 300 ms inside a Worker — pings stay flat at their normal spacing, the loop never noticed; `[3]` I/O-bound load (pbkdf2 on the thread pool) — pings flat again, with zero extra threads: the event loop already handles waiting for free.
