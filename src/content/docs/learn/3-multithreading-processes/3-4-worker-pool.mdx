## What you will learn

A `new Worker` is ~30 ms of spawn plus a full V8 heap, every time. Spawn one per job and those costs scale with your traffic — 8 jobs, 8 spawns, 8 concurrent heaps at peak. The **worker pool** pattern is the fix, and it is three ideas: spawn a fixed number of workers once; hand work out by message instead of by spawn; keep a queue so a burst waits instead of spawning a storm. What you buy is not usually wall-clock — on a many-core box one-shot workers can keep up — it is *boundedness*: spawns and peak workers stay constant however many jobs arrive. Sizing has a rule of thumb for the common case: pool = CPU cores for CPU-bound work, because beyond cores the jobs only queue against each other.

<Pitfall title="Worker not thenable — 'await worker' resolves instantly">
	<p>
		A `Worker` object has no `then` method. `await worker` resolves on the spot, before the work has even started, and the code after it happily reads half-finished state. Wait on the `exit` event — `new Promise((resolve) => worker.on('exit', resolve))` — or better, on the worker's reply message. Same family of bug: don't `await` a stream or an EventEmitter expecting it to "finish"; `await` only knows promises.
	</p>
</Pitfall>

## Counts, not times

Run the demo file for this lesson:

```bash
node code/3-multithreading-processes/3-4-worker-pool/demo.js
```

It prints: `[1]` spawn-per-job — 8 spawns, peak 8 concurrent workers, spawn cost paid 8 times; `[2]` a pool of 4 on the same 8 jobs — 4 spawns, each worker runs 2 jobs (proven by `threadId` counts), reuse visible; `[3]` a burst of 20 into the same pool — spawns and peak stay at 4 while the queue drains 16 → 0, nothing lost, no spawn storm. Watch the wall-clock line honestly: on a big machine [1] may match [2]; trust the counts.
