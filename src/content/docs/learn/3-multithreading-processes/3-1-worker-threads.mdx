## What you will learn

`new Worker(file)` builds a second V8 isolate with its own event loop, running on its own OS thread, inside the same process — one `pid`, two `threadId`s. Nothing is shared between the two isolates by default, which is the feature: no locks on the JS heap, because there is no shared JS heap. Communication goes through `postMessage`, and its two modes are the heart of this lesson. Without a transfer list the message is **structured-cloned** — the runtime walks the value and copies it, so a 64 MB `ArrayBuffer` costs a 64 MB copy and the sender keeps its copy. With the buffer listed in the transfer list, the backing memory is **moved** — the receiver gets the bytes, the sender's view is detached (`byteLength === 0`) the instant `postMessage` returns. Zero copy, and the sender physically cannot touch the data again.

<Pitfall title="Transfer detaches the buffer immediately — before the worker sees it">
	<p>
		`postMessage(msg, [buf])` neuters the sender's `buf` at call time, not when the worker reads it. Code after the call sees `byteLength === 0` — any later `postMessage` of the same buffer throws `DataCloneError`. And **MessageChannel** is the third port pair you will meet: it is how two workers talk *directly*, without the parent relaying. Build a channel, hand one port to each side, and messages flow between them without the main thread in the loop.
	</p>
</Pitfall>

## One process, two threads, two postMessage modes

Run the demo file for this lesson:

```bash
node code/3-multithreading-processes/3-1-worker-threads/demo.js
```

It prints: `[1]` the main thread's `threadId` and pid; `[2]` the worker's — same pid, different `threadId`, the two-isolate picture made visible. `[3]` a 64 MB buffer sent without a transfer list: worker gets the bytes, main's copy still full — a clone, a full copy. `[4]` the same buffer transferred: main's `byteLength` reads `0` immediately after `postMessage`, worker gets the same memory — moved, not copied.
