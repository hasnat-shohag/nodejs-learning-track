## What you will learn

Two memory ceilings, two failure modes. The **stack** holds call frames, is capped by depth (~12k frames default), and overflows with a *catchable* `RangeError`. The **heap** holds objects, is capped by `--max-old-space-size` (~2–4GB by default), and overflows by *killing the process* — SIGABRT, no exception, no `finally` blocks. This lesson triggers both on purpose and reads the OOM output the way production demands: what was allocating, in which space, when the limit hit.

<Pitfall title="--max-old-space-size caps OLD space only">
	<p>
		The flag does not cap the whole heap: new space (young generation), code space, and large-object space sit outside it — so a process with `--max-old-space-size=512` can legitimately use ~600MB RSS. Tune it from the <strong>old space</strong> number in `v8.getHeapSpaceStatistics()`, not from container RSS. And when raising it: if the growth is a leak, a bigger heap just delays the crash and lengthens the major-GC pauses.
	</p>
</Pitfall>

## Trigger both failures

Run the demo file for this lesson:

```bash
node code/2-v8-memory-modules/2-2-heap-stack-limits/demo.js
```

`[1]` recurses to `RangeError` at ~12.5k frames — caught, printed, process continues. `[2]` shows heap growth is just numbers moving until a limit. `[3]` spawns a child with `--max-old-space-size=64` and lets it die: the parent reports the SIGABRT signal and reads the child's stderr stacktrace — V8 frames naming the allocation site, not a JS `throw`. The contrast is the lesson: **stack overflow is an exception; heap exhaustion is a shutdown**.
