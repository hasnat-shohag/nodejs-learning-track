## What you will learn

V8 is not an interpreter — it is a tiering compiler. Your code starts as bytecode (Ignition), and functions that run hot get recompiled to optimized machine code (TurboFan). Optimization decisions are built on **shapes**: objects constructed with the same properties in the same order share one **hidden class**, letting V8 inline property access. Scatter your shapes and every property read falls back to slow lookups. This lesson measures all three facts — shape divergence, inline-cache overflow, and the GC spaces your pauses come from.

<Pitfall title="Deopt is silent and per-function">
	<p>
		TurboFan compiles a function <em>assuming</em> the types it has seen. Feed it a different shape once — `null` where objects always were, a fifth constructor where four ran — and V8 throws away the optimized code (deopt) and recompiles from bytecode. No warning prints; the function just gets slower. The fix is not micro-tuning: keep hot paths monomorphic — one shape, one type, stable arguments.
	</p>
</Pitfall>

## Three measurements

Run the demo file for this lesson:

```bash
node code/2-v8-memory-modules/2-1-v8-server-view/demo.js
```

It prints: `[1]` one construction order vs `[2]` three orders interleaved — the scattered set reads ~1.7x slower because its hidden classes fork; `[3]` four shapes rotating through one read site — the inline cache overflows to megamorphic lookup; `[4]` the actual V8 heap spaces of the running process, so "young generation" and "old space" stop being vocabulary and become megabytes.
