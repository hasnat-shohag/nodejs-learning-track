## What you will learn

`require()` is a cache lookup keyed by resolved filename — the second call returns the *same* exports object, and the cache is writable (`delete require.cache[...]` forces a reload). ES modules are a different machine: the loader **resolves and links the whole graph first**, then evaluates modules depth-first. Circulars break both systems, differently: CJS hands one side a **partial exports object** (with a warning) — always, whichever side you enter from. ESM is subtler: a top-level circular read **TDZ-throws only when the reader module evaluates before the exporter**; entered the other way, the same read works. But ESM bindings are *live* in every order, so a read deferred to call time always sees the current value. This lesson runs all four behaviors and shows where each system's escape hatch is. (One more Node 22 fact worth knowing: `require()` of an ESM-only `.mjs` file now works without flags, quietly dissolving the "two systems, no bridge" confusion.)

<Pitfall title="package.json type decides, extension does not override">
	<p>
		`.cjs` is always CJS, `.mjs` is always ESM, and a bare `.js` follows the <em>nearest package.json's</em> `"type"` field. The same file can be a different module system depending on where it sits — which is why "it works in the repo but not in the published package" is so often a type-field mismatch. Dual-publishing (`"exports"` with both conditions) hides this until first `require`, not at install.

## Four behaviors, one run

Run the demo file for this lesson:

```bash
node code/2-v8-memory-modules/2-4-module-internals/demo.js
```

It writes real modules to a temp dir and exercises them: `[1]` two `require()` calls return the identical object — mutate one, both see it. `[2]` deletes the cache entry and re-requires: fresh state, different object. `[3]` a circular `require` where `second.cjs` sees `first.firstValue === undefined` — the half-built exports — plus Node's circular-dependency warning on stderr. `[4]` the same cycle in ESM, entered from *both sides* in separate child processes: via the reader's entry, the exporter evaluates first and the top-level read is fine; via the exporter's entry, the reader evaluates first and the same read throws `ReferenceError: Cannot access 'aValue' before initialization` — then a call-time read returns the live value in both orders. Check stderr for both warnings; they are the systems telling on themselves.
