## What you will learn

`http.createServer(handler)` costs nothing — it builds an object and returns. The server only becomes real at `.listen()`: Node binds, the kernel assigns a socket, and the `'listening'` event fires with the address available at `server.address()`. From then on two event layers run: `'connection'` hands you a raw `net.Socket` (the TCP layer), and `'request'` rides on top of each socket as **parsed** HTTP — an **IncomingMessage** (method, url, headers, and the body as a readable stream) and a **ServerResponse** (a writable stream plus `writeHead`/`end`). The layering is the performance story too: HTTP/1.1 keep-alive means one TCP connection carries many requests, so the expensive part (connection setup) is paid once and amortized. The demo's three requests ride a single connection — `connection` fires once.

<Pitfall title="server.close() waits for keep-alive sockets — the process hangs open">
	<p>
		`server.close()` stops accepting *new* connections but existing keep-alive sockets stay open, so a script that calls `close()` and waits for the callback can hang forever with idle clients holding sockets. The fix is `server.closeAllConnections()` (Node 18.2+), or close from the client side. Same family: `server.listen(port)` with port `0` asks the kernel to assign — read the real port from `server.address().port` in the `'listening'` callback, never assume.
	</p>
</Pitfall>

## One server, two event layers

Run the demo file for this lesson:

```bash
node code/4-http-server-scratch/4-1-server-lifecycle/demo.js
```

It prints: `[1]` `createServer()` returned with `listening === false` — nothing happens until `.listen()`; `[2]` the `'listening'` event with the kernel-assigned port; `[3]` what the handler actually receives for a `POST /hello?x=1` — method, url, HTTP version, all pre-parsed; `[4]` three requests delivered over ONE TCP connection — keep-alive amortizing the handshake.
