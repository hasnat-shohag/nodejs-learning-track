## What you will learn

`monitorEventLoopDelay()` from **perf_hooks** returns a histogram that samples the gap between loop turns — the true latency of the process, as felt by every request and timer. A ~90ms blocking `pbkdf2Sync` call freezes the loop mid-turn, and the histogram records it as a delay spike of the same size — but only with `resolution: 1` and only after one *more* turn runs: a coarse sample interval, or disabling too early, makes the same stall look tiny or invisible, which is exactly the demo's cautionary note. The stall seen from the timer side is the same fact: a 20ms `setInterval` ticker runs ~85ms late, because the tick due during the block queues behind it. Latency SLA breaches show up here before any dashboard notices — every queued request and timer waits the full gap. When inside-the-process instruments are not enough, **--inspect** (or `SIGUSR1`) opens a DevTools debugging channel to a live server, and a heap snapshot answers "what is eating the memory" when rss creeps up. Both are last-resort tools for diagnosis, never routine operation: the metrics you *watch* are loop delay, rss drift, and event-loop lag percentiles — the stall detector that runs while you sleep.

<Pitfall title="A coarse resolution hides the spikes you installed it to catch">
	<p>
		`monitorEventLoopDelay({ resolution: 5 })` samples every 5ms; a 90ms stall sampled that way read as `max 5.4ms` in the demo — the spike averaged away. And the big gap is only recorded on the *next* loop turn after the block: call `disable()` too early and the histogram misses the very stall you caused. Pick `resolution: 1` for diagnosis, and let the loop turn once before you read it.
	</p>
</Pitfall>

## Watch the loop from inside, attach from outside

Run the demo file for this lesson:

```bash
node code/5-production-server/5-6-diagnostics/demo.js
```

It prints: `[1]` a ~90ms blocking call measured by `monitorEventLoopDelay` at `resolution: 1` — the stall as the loop felt it, with the coarse-resolution warning; `[2]` the same stall from the timer side — a 20ms ticker firing ~85ms late, drift equal to the block; `[3]` the prod checklist from inside the process: rss/heapUsed for leak candidates, `--inspect`/`SIGUSR1` for the debugger, heap snapshots when rss climbs.
