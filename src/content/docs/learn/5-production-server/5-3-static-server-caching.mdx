## What you will learn

Caching is a contract between your server and the browser, signed in headers. The **ETag** is a stamp *of the body* — here, the first 16 hex chars of its SHA-256 — and the browser's half of the deal is re-sending it as `If-None-Match` when the policy says revalidate. If the stamp still matches, you answer **304 Not Modified** and send *zero* body bytes; the browser reuses its cached copy and the wire only paid for headers. If the file changed, the new body hashes differently, the stamp moves, and the client gets a full 200 with fresh bytes — the demo shows both sides by capturing the old ETag *before* overwriting the file. **Cache-Control** states the policy: `public, max-age=60` lets the browser reuse without asking for a minute; `no-cache` forces revalidation every time; `no-store` forbids saving at all. The one sentence to remember: ETag says *what* the body is, Cache-Control says *how long the copy may be trusted* — and neither is useful without the other.

<Pitfall title="Stamp the bytes you actually send">
	<p>
		An ETag computed from the *file on disk* lies the moment you transform before sending — gzip, templating, partial content. Wrong stamp means a 304 for a body that differs, and the browser serves stale bytes with your blessing. Hash the exact buffer that leaves the server, and recompute it whenever the response can vary (compression on/off, language negotiation).
	</p>
</Pitfall>

## Stamp, policy, and the free 304

Run the demo file for this lesson:

```bash
node code/5-production-server/5-3-static-server-caching/demo.js
```

It prints: `[1]` a first GET — content-type by extension, `etag` and `cache-control` on the reply; `[2]` the re-GET carrying `If-None-Match` — 304, body bytes: 0; `[3]` the file rewritten between requests — old stamp sent, new body back, 200, and the ETag moved with the content.
