## What you will learn

The request object your handler receives *is* a Readable stream, and an upload is nothing special: bytes arriving over time. The streaming server pipes each `'data'` chunk into a `createWriteStream` — chunk → disk, never chunk → RAM → disk — and its heap stays flat (~7MB before, ~7.6MB during) while a 20MB upload lands, and stays just as flat with two 20MB uploads interleaved. The naive server that collects every chunk into an array and `Buffer.concat`s on `'end'` holds all 20971520 bytes in memory at once; multiply by concurrent uploads and that is your 3 AM OOM. **Multipart uploads** — what browsers send for `<input type="file">` — change nothing structural: the body is a Readable whose bytes carry boundary markers, so you slice on boundaries *while* streaming. The real-world discipline is boundedness: pick a max body size and reject early, because "stream it" still means "let the client send me anything".

<Pitfall title="Unbounded body = client-chosen memory usage">
	<p>
		A handler with no length check lets the client decide how much data your process holds. Set a ceiling: read `content-length` when present, and count bytes as chunks arrive — past the limit, destroy the request and answer 413. Streaming protects you from *accidents*; a limit protects you from *clients*.
	</p>
</Pitfall>

## Chunk to disk, never chunk to RAM

Run the demo file for this lesson:

```bash
node code/5-production-server/5-2-streaming-uploads/demo.js
```

It prints: `[1]` a 20MB upload in 64KB slices landing on disk — server heap before/during proving the body never lived in RAM; `[2]` two of them concurrently, heap still flat while chunks interleave; `[3]` the anti-pattern — the same upload held whole in memory, 20MB at once, the number your container limit reads.
